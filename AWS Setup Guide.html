1. はじめに・決定事項まとめ

このガイドは C:\Users\student\code\ai2(CARE SEC 転倒・異常検知)を AWS へ移す手順書です。 Windows開発機特有の事情(USBカメラ2台・Frame Server・venv)はクラウドに持っていけないので、 「AIエンジン単一プロセス」と「録画ファイルのプライバシ保護」を軸に構成します。

項目決定理由
OSUbuntu 26.04 LTS希望指定。LTSサポート~2031。Python 3.13 が標準で ai2 の開発環境と同系列
インスタンスタイプt3.large(2vCPU/8GiB)— 妥当実測根拠: TF2.20+MediaPipe+CLIP(torch)同居で RSS 約4〜5GB、CPUは2台間引きpose≈5/s×2+推論7ms で 2vCPU に収まる(開発機の有人27fpsはUSB側の数字)
リージョンap-northeast-1(東京)施設からのレイテンシ最小。データは国内に置く(介護記録は機微)
DB当面 SQLite + EBSスナップショット、将来 RDSai2 は SQLite 前提設計(db.sqlite3 単一ファイル)。小規模施設なら EBS 完結で十分
録画/画像保存インスタンス上の EBS(media/)+ バックアップS3パブリック bucket は使わない(プライバシ)。S3に出すなら Presigned URL 方式のみ。第8章
Webnginx + gunicorn(systemd常駐)requirements.txt に gunicorn==23.0.0 済み
AIエンジンgunicorn 起動の同一プロセス内で常駐(apps.py スレッド)workers は必ず 1。複数にするとAIスレッドが二重起動し、_claim_ai_lock で1つ以外シャットアウトされる(設計どおりだが無駄)
開発環境と本番の既知の差分を先に理解する
・tensorflow: Windows 2.21.0 / Linux 2.20.0(requirements.txt に意図した差分として明記済み)
・CLIP: requirements.txt には torch 系がまだ無い → 第7章の「Linux向け追記」を必ず適用
・USBカメラ: EC2 には刺さらない → IPカメラ(RTSP/MJPEG)または Pi 配信で運用(第12章・第3章)

3. 移行パターン選定(重要・ここを先に決める)

パターンA: 全部AWS(IPカメラ/Pi配信)パターンB: ハイブリッド(エンジンは手元PC)
構成カメラ映像を RTSP/MJPEG で EC2 が入力。Web・DB・AI全て EC2USBカメラ+AI解析は開発機で継続、Web/DBだけ AWS。AIは API 経由でアラートを書き込む
良い点1台で完結・停電時PC停止に依存しない・運用が単純。ai2 は IPカメラ対応済み(Camera.stream_url)既存のカメラ環境をそのまま使える・帯域節約
弱点回線断=全停止・帯域(台数×2〜3Mbps)が必要AWS側の「ライブ画面」が使えない・DB二重化(同期)問題・手元PCが常に必要=クラウドの意味が減る
判定推奨(本ガイドはこの構成)移行の過渡期だけ
結論: パターンA。ai2 は既に IPカメラ(network_sources(): rtsp:// / http(s):// MJPEG)を第一級対応しており、USB特有の対策(DSHOW順序・Frame Server・検知総当たり)はネットワークカメラでは問題になりません。Pi 配信基線は過去の作業で確立済みです。

4. ネットワーク: VPC・サブネット(AWS CLI版)

個人〜小施設規模ならVPC1個・publicサブネット1個・IGW1個が正解です。 「VPC=難しいもの」ではなく論理的内線電話網(自分専用の私的ネットワーク)だと思っていると楽になります。

4.1 コンソールで作る場合(1回やれば覚える)

  1. VPCダッシュボード → VPCの作成 → 「VPC、パブリックサブネット、インターネットゲートウェイ」プリセット
    • 名前: caresec-vpc / IPv4 CIDR: 10.0.0.0/16 / サブネット1つ(10.0.1.0/24、AZ: ap-northeast-1a)
    • このプリセットは NATゲートウェイを作らない(=NATの時間課金≈¥300/日を回避)。単一公開サーバーでは不要
  2. EC2起動時に対象サブネット+自動割当パブリックIPを指定(第6章)
  3. Elastic IP を1個確保しインスタンスに紐付け(再起動・再作成でIPが変わらないようにする)

4.2 CLIで作る場合

# 前提: aws configure (IAMユーザー or SSO。ルートアカウントのアクセスキーは作らない)
VPC_ID=$(aws ec2 create-vpc --cidr-block 10.0.0.0/16 \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=caresec-vpc}]' \
  --query Vpc.VpcId --output text)

SUBNET_ID=$(aws ec2 create-subnet --vpc-id $VPC_ID \
  --cidr-block 10.0.1.0/24 --availability-zone ap-northeast-1a \
  --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=caresec-public}]' \
  --query Subnet.SubnetId --output text)

IGW_ID=$(aws ec2 create-internet-gateway \
  --tag-specifications 'ResourceType=internet-gateway,Tags=[{Key=Name,Value=caresec-igw}]' \
  --query InternetGateway.InternetGatewayId --output text)
aws ec2 attach-internet-gateway --vpc-id $VPC_ID --internet-gateway-id $IGW_ID

# この VPC の「デフォルトルートテーブル」に 0.0.0.0/0→IGW を入れる(public化)
RT_ID=$(aws ec2 describe-route-tables --filters Name=vpc-id,Values=$VPC_ID \
  --query 'RouteTables[0].RouteTableId' --output text)
aws ec2 create-route --route-table-id $RT_ID --destination-cidr-block 0.0.0.0/0 \
  --gateway-id $IGW_ID
# サブネットが自動でデフォルトRTに関連付くので追加作業なし(新規サブネットは自前関連付けが必要な場面あり)

# Elastic IP
EIP_ID=$(aws ec2 allocate-address --domain vpc \
  --tag-specifications 'ResourceType=elastic-ip,Tags=[{Key=Name,Value=caresec-eip}]' \
  --query AllocationId --output text)
echo "VPC=$VPC_ID SUBNET=$SUBNET_ID IGW=$IGW_ID EIP=$EIP_ID"

5. ファイアウォール: セキュリティグループ(SG)・NACL・OS層

AWSの「ファイアウォール」の主役はセキュリティグループ=インスタンスに貼る許可リスト(stateful)です。 stateful=「入り口を開けた通信の戻りは自動で通る」ので、出口ルールは基本全部許可のままで動きます。 NACLは無状態のサブネット幅のフィルタで、単一構成ならデフォルトのまま触らないのが正解(触るとハマる)。

5.1 SG設計(CARE SEC用マトリクス)

用途タイプポート送信元説明
Web公開IngressTCP 4430.0.0.0/0唯一の一般公開窓口。HTTPSのみ
HTTP→HTTPS誘導IngressTCP 800.0.0.0/0nginxで301リダイレクトのみ。コンテンツは流さない
SSHIngressTCP 22施設/事務所のグローバルIP/32 のみ固定IPが無い場合は都度更新、または Session Manager で22を開けない運用に(5.3)
カメラ映像取り込み———不要。Pi→EC2の「外方向」接続で受けるため、AWS側の Ingress は増えない(第12章)
出口EgressALL0.0.0.0/0既定のまま。apt/pip/SMTP/HFモデルDLが必要
絶対に開けないポート: 8000(gunicorn)/3306/5432(将来のDB)/8554 等の RTSP を 0.0.0.0/0 にしない。gunicorn は 127.0.0.1 待ち受ければもう十分です(第7章)

5.2 作成コマンド

SG_ID=$(aws ec2 create-security-group --group-name caresec-web \
  --description "CARE SEC production" --vpc-id $VPC_ID \
  --tag-specifications 'ResourceType=security-group,Tags=[{Key=Name,Value=caresec-web}]' \
  --query GroupId --output text)

aws ec2 authorize-security-group-ingress --group-id $SG_ID --protocol tcp --port 443  --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id $SG_ID --protocol tcp --port 80   --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id $SG_ID --protocol tcp --port 22   --cidr 203.0.113.55/32   # ←自分のIPに変えろ
echo "SG=$SG_ID"

# 送信元IPが変わったら(施設動的IP):
aws ec2 revoke-security-group-ingress --group-id $SG_ID --protocol tcp --port 22 --cidr 203.0.113.55/32
aws ec2 authorize-security-group-ingress --group-id $SG_ID --protocol tcp --port 22 --cidr <新IP>/32

5.3 SSHポートも開けたくない場合(AWS Systems Manager)

  1. IAMでインスタンスロール caresec-ec2 に AmazonSSMManagedInstanceCore を付与(第11章)
  2. EC2にアタッチ → SGの 22 を閉じたまま、コンソールの「接続→Session Manager」でシェル进入
  3. 秘密情報は一切ポートにしない。監査ログ(CloudTrail)も残る

5.4 OS層の二重防火墙(深防御)

SGが効きすぎて「何もかも不通」になるときは、SGのせいにしたくなるが OS の ufw/iptables/fail2ban の場合もある。 層を分けて考える: SG(クラウド) → ufw(ホスト) → アプリ許可(Djangoの権限)。 管理を単純にするため、本ガイドでは ufw はループバック+443/80/22 のみ許可の最小構成にし、 「細かいことはSGでやる」と役割分担します。

sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw logging low
sudo ufw enable
sudo ufw status verbose

6.2 user-data(起動時自動セットアップ)

#!/bin/bash
set -euxo pipefail
export DEBIAN_FRONTEND=noninteractive

# 時刻はJST(介護記録のタイムスタンプ命)
timedatectl set-timezone Asia/Tokyo

apt-get update
apt-get -y upgrade
apt-get -y install \
  python3 python3-venv python3-pip git nginx \
  build-essential libgl1 libglib2.0-0 ttf-wqy-zenhei \
  unattended-upgrades fail2ban logrotate

# スワップ4GB(t3.large 8GiB+AI。学習/モデルロードの瞬間ヒックリ防止)
if [ ! -f /swapfile ]; then
  fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
  echo '/swapfile none swap sw 0 0' >> /etc/fstab
fi
sysctl vm.swappiness=10
echo 'vm.swappiness=10' > /etc/sysctl.d/99-caresec.conf

# 自動セキュリティ更新
cat > /etc/apt/apt.conf.d/20auto-upgrades <<EOF
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
EOF

mkdir -p /opt/care-sec
useradd -r -m -s /usr/sbin/nologin caresec || true
libgl1 libglib2.0-0 は OpenCV/MediaPipe が実機で要求するGUI系共有ライブラリです(requirements.txtのコメント済の通り)。「import cv2 で落ちる」対策の最初の一歩。

7.4 gunicorn systemdユニット(workers=1が生命線)

sudo tee /etc/systemd/system/caresec.service > /dev/null <<'EOF'
[Unit]
Description=CARE SEC (Django + AI engine)
After=network-online.target

[Service]
User=caresec
Group=www-data
WorkingDirectory=/opt/care-sec/ai2
EnvironmentFile=/etc/care-sec.env
# workers=1 threads=8 — AI常駐スレッドはプロセス内に1つだけ。
# 複数workerは二重検知ではなく「2番目以降がロックで寝る」だけ無駄が出る。
ExecStart=/opt/care-sec/ai2/.venv/bin/gunicorn config.wsgi:application \
  --bind 127.0.0.1:8000 --workers 1 --threads 8 \
  --timeout 120 --graceful-timeout 30 --access-logfile - --error-logfile -
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now caresec
sudo systemctl status caresec --no-pager
# 起動ログに「AIモデルの準備が完了しました(~秒 / 転倒=3名)」と「常時稼働を開始しました: index [...]」が出ればAIも生きている
sudo journalctl -u caresec -f | grep -E "RealtimeAI|Retrain|Traceback"
127.0.0.1 bind が重要。0.0.0.0:8000 で待ち受けると、SGで8000を閉じても OS の ufw を開けた瞬間に認証なしAPIが互联网に露出します。入口は nginx(443)だけに一本化する。

8. メディアパスを「ログインしているユーザーのみ」に表示する(本ガイドの核心)

8.1 現状のままだと何が危険か

開発機の runserver(DEBUG=1)では /media/… を Django が素で配信していますが、本番 nginx で location /media/ { root … } と静态配信すると——

URL を知っている誰でも、録画mp4(入居者の顔・裸体・居室)と検知スナップショットが見られます。
・検索エンジンのキャッシュ / SMSで共有されたURL / ログに残った Referer … すべて漏洩経路。
・介護施設では「録画が見られるURL」=プライバシ侵害そのもの。認証なしの静的配信は不可。

8.2 方式の選択

方式仕組み採用?
① Django が保護配信(FileResponse)URLは /media/… のまま、nginxはプロキシのみ。Djangoのログイン判定→ファイル送信採用(ai2 に追加・第8.3章)。録画は1本~数百KBの短尺なので十分軽い
② nginx X-Accel-RedirectDjangoは認可だけ返し、ファイル転送は nginx 内部 location が担当(高速・Djangoを転送で生かささない)規模拡大時に①から差し替え可(第8.5章)
③ S3 + Presigned URLファイルはS3、短期署名URLをDjangoが発行将来の拡張。EBS十分なら当面不要
④ 基本認証(nginx auth_basic)で /media だけ二重ロックDjangoログイン+別途パスワードログインが二重になりUX悪。保険としてなら可

8.3 ai2 側の追加コード(方式①・今すぐこれ)

新規ファイル core/protected_media.py:

# -*- coding: utf-8 -*-
"""media/ 配下のファイルを『ログイン済みユーザーだけ』に配信する(view)

開発の runserver(DEBUG=1)では Django が /media/ を素で配信してしまうため、
本番の main ブロックの urlpatterns にこの view を差し込み、
nginx は /media/ を静态配信せず Django(gunicorn)へプロキシする。
"""
import mimetypes
import os
from pathlib import Path

from django.conf import settings
from django.http import FileResponse, Http404
from django.contrib.auth.decorators import login_required


@login_required
def protected_media(request, path):
    root = Path(str(settings.MEDIA_ROOT)).resolve()
    target = (root / path).resolve()
    # パストラバーサル防御(/media/../../etc/passwd 等)
    try:
        target.relative_to(root)
    except ValueError:
        raise Http404("media 外を指定できません")
    if not target.is_file():
        raise Http404("ファイルが存在しません")

    ctype, _ = mimetypes.guess_type(str(target))
    response = FileResponse(
        target.open("rb"),
        content_type=ctype or "application/octet-stream",
        # mp4 の範囲要求(Range)は FileResponse が素では対応しないため
        # 短尺録画(数秒〜1分)で十分ならこのまま。「シーク多用」なら 8.5 の X-Accel へ
    )
    response["X-Frame-Options"] = "SAMEORIGIN"
    response["Cache-Control"] = "private, max-age=300"   # ブラウザだけ短期キャッシュ
    return response

config/urls.py — 現状「開発用」で生やしている static() マウントを本番で閉じる:

# 現状(開発用・settings.DEBUG で無条件):
#   urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
# 変更: DEBUG のときだけ static()、本番は保護viewで受ける
from django.conf import settings
from core import protected_media

if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
else:
    urlpatterns += [
        re_path(r"^media/(?P<path>.+)$", protected_media.protected_media, name="protected_media"),
    ]

※ re_path を django.urls から import 追加を忘れずに。URLの形(/media/recordings/ai_fall_….mp4)は Recording.video_url に保存済みの値とそのまま一致するので、既存レコード・テンプレ・DB移行は変更不要です。

8.4 nginx 設定(①方式 / 第9章のTLSと一体)

server {
    listen 80;
    server_name secure.example.or.jp;
    return 301 https://$host$request_uri;
}

server {

    # 証明書は第9章

    ssl_certificate_key /etc/letsencrypt/live/secure.example.or.jp/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # 静的(css/js)= 公開してよい。媒体は絶対ここに入れない
    location /static/ {
        alias /opt/care-sec/ai2/staticfiles/;
        expires 7d;
        access_log off;
    }

    # ★ media は静态配信しない。何も書かなければ以下のプロキシに流れ
    #   Django(protected_media view)がログイン判定してから出す

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 120s;
        client_max_body_size 50m;
    }
}

settings.py に SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https") を追加(nginxの X-Forwarded-Proto を信頼して https 扱いにする。ないとリダイレクトループや cookie secure の矛盾が起きる)

8.5 (任意・高性能版)X-Accel-Redirect に切り替える

# nginx: /protected/ は internal(=外部URLとして絶対通さない)。実体はここ
location /protected/ {
    internal;
    alias /opt/care-sec/ai2/media/;
}

# views(Django): 認可だけ判定し、転送は nginx に投げる
def protected_media(request, path):
    # (root内チェック・is_fileチェックは 8.3 と同じ)
    response = HttpResponse(status=200)
    response["X-Accel-Redirect"] = f"/protected/{path}"
    response["Content-Type"] = mimetypes.guess_type(path)[0] or "application/octet-stream"
    return response

これで「Djangoは関門だけ、太いパイプは nginx」になり、mp4のRange再生・大量視聴にも強くなります。

8.6 漏洩していないかの検証手順(必ず実施)

# ① 認証なし=弾かれること
curl -s -o /dev/null -w "%{http_code}\n" https://secure.example.or.jp/media/recordings/ai_fall_20261120-101045_cam3.mp4
#   → 期望: 302(/accounts/login/ へ) または 403。 200 が返ったら設定ミス

#   → 200
# ③ パストラバーサル
curl -s -o /dev/null -w "%{http_code}\n" "https://…/media/../db.sqlite3"     # → 400/404
# ④ 念のため robots・キャッシュ検索: google.com で site:あなたのドメイン media を確認(出ていたら要無効化申請)

12. カメラ接続(Pi / IPカメラ → AWS)

USBカメラはクラウドに刺せないので、カメラ入力全てをネットワークカメラ化する。ai2 は本機能対応済み (Camera.stream_url に rtsp:// / http(s)://…mjpeg… を入れるだけ)。

12.1 2つの接続形

形流れAWS側SG備考
Pull(EC2→Pi)EC2が rtsp://192.168.x.x:8554 を開く要ハブ: Pi側を公网に開くのは論外。Site-to-Site VPN or DS が必要施設グローバルIP固定なら可だが運用重い
Push(Pi→EC2)推奨Pi が RTMP/WebSocket/HTTPストリームをEC2へ外向きで送り続ける。ai2は「IP配信済みカメラ」を http(s):// で取れる443/80だけ=既存SGのまま既存「Pi配信」資産がそのまま使える。帯域は1.5〜3Mbps/台

12.2 帯域・レイテンシ予算(設計基準)

台数        受信帯域(640x480@MJPEG相当)   想定CPU(解析)
2台   →  4〜6 Mbps           t3.large で余る(間引きpose≈5/s/台)
4台   →  8〜12 Mbps          pose 2〜3/s/台に落ちる→ t3.xlarge か AI分割
8台   →  20+ Mbps           単一t3.largeは不可。AI専用機分離(第3章Bの応用)

施設回線はアップロード側(Pi→AWSは施設の下りではなく上り)。光電話セットの「1Gbps」は下り話で、上りは 100〜200Mbps あるが、IPv4過剰共有(OCN等)は上りが弱いので実測(iperf3)してから台数を積み増すこと。

12.3 別解: Tailscale で「同一ネットワーク」にして Pull 型を安全に使う

第12.1表の Pull(EC2→Pi)は「Piを公网に開けないと無理」と書いたが、Tailscale(WireGuardベースのメッシュVPN)で EC2とPiと事務所PCを同じ仮想的なLAN(100.64.0.0/10)にすると、この制約が消える。

 施設LAN                     AWS VPC
 ┌─────────┐  Tailscale   ┌──────────────┐
 │ Pi(100. │◄══メッシュ══►│ EC2(100.64.  │
 │ 64.1.2) │  自動NAT通過 │ 2.3)+事務所PC │
 └─────────┘  (hole punch)└──────────────┘
   EC2から rtsp://100.64.1.2:8554 を「LAN内のカメラ」として開ける
   施設側: グローバルIP不要・ポートフォワード不要・CGNAA(OCN等)でも大体OK
観点Push型(第12.1・既定)Tailscale Pull型
設定の手軽さPiに配信仕込み済みなら最速(ai2既存機能のみ)EC2/Pi各にtailscale upのみ。ルータ設定ゼロは施設運用で大きい
AWS SG/公開面443/80(既存)443/80のまま+22を閉じたままSSH可能(SGを100.64.0.0/10に絞れる)。公開窓口が減るのはセキュリティ上むしろ◎
帯域リスク施設の上りを常に使うUDP hole punch成功なら同じ。失敗してDERP中継に落ちた時だけ映像がカクつく/無料枠の中継スループット制限が効く(実測必須)
依存・障害点なしTailscaleのコントロールプレーン(鍵認証)。既存の直結セッションは暫く維持されるが、全経路DERP経由環境では影響大
料金¥0Personal Free(3ユーザー/100デバイス)で今回の規模はほぼ足る。事業運用なら Pro($6/user/月 目安)を推奨=経理に説明可能な構成にする
プライバシ映像はAWSまで自前TLS/RTSPメッシュ内はWireGuard暗号だが、中継(DERP)が通ると映像バイトがサードパーティAWSリージョンを通過し得る。介護映像なので契約・ plans を事前に精読(自前headscaleで回避可)

導入手順(両端で計5分)

# EC2(Ubuntu 26.04)
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --ssh          # ブラウザで承認。--ssh で Tailscale SSH(鍵配布不要)
tailscale ip -4                  # → 100.64.x.x を控える

# 各 Pi
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --authkey tskey-…   # 施設分を無人承認(スクリプト展開向き)

# SG: Tailscaleの直結通信のために UDP 41641 を inbound(送信元 0.0.0.0/0 で可:
#     WireGuard鍵で認証されるので「ポートが開く」の意味は通常と違う)
aws ec2 authorize-security-group-ingress --group-id $SG_ID \
  --protocol udp --port 41641 --cidr 0.0.0.0/0

# ai2 カメラスケジュール: stream_url を LAN address のまま書ける
#   rtsp://100.64.1.2:8554/ch0   ← Piのtailscale IP
#   ※ 施設内LAN IP(192.168.x.x)をそのまま使いたい場合は Pi側サブネットで
#     VPC Peering/Site-to-Site VPN が正解。Tailscale は 100.64/10 名義で統一する
結論:「簡単か?」→ 初期設定は Tailscale の方が楽(ルータ設定がゼロで、22まで閉じられる)。 ただし常時映像の主経路としては Push 型を第一候補に置き、 ①Pull型がやりたい / ②SSH公開ポートを消したい / ③複数拠点を1画面に集約したい、のどれかに当たったら Tailscale を採用するのがうまい使い方。 ai2 側は IPカメラの URL を変えるだけなので後から切り替え自由(まずPushで始めて、運用が見えてから Pull+Tailscale に寄せる移行も可)。
