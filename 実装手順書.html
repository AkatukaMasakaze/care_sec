この手順書について

templates/ 配下の全画面に表示されているボタン・表示項目を洗い出し、 それぞれが現在のバックエンドで動くかをコードと突き合わせて確認しました。 本書は「まだ動かない/見かけだけの機能」を動く状態にするまでの手順を、画面単位でまとめたものです。

凡例意味
実装済現在のコードで動く。作業不要
要修正動くが不具合・見かけだけ・デモ値固定などがある
未実装画面にはあるがバックエンドが無い(またはエラーになる)
任意無くても画面は成立するが、運用上あった方がよい
最初に確認してほしいこと INTEGRATION_STATUS.md には core/ai_engine.py・core/training.py・ai_models/ などを 実装・検証済みと書かれていますが、これらはリポジトリに含まれていません(別マシンの作業フォルダに残っていると思われます)。 そのファイル一式が手元にあるなら、アップロードするのが最短です。本書の STEP 7〜8 は、それが無い前提で 同等の機能を最小構成で作り直す手順です。
サンプルコードの扱い サンプルは既存コードの命名・構成に合わせて書いています。Python部分は構文チェックのみ実施しており、 カメラ・TensorFlow・MediaPipe を使う部分はこの環境では実行確認していません。 組み込み後は STEP 9 の検証を必ず実施してください。

STEP 1. 共通レイアウト(base.html)

1-1 操作結果メッセージを表示する 未実装

「対応を担当しました」「解決報告を保存しました」「AI監視を停止しました」などは ビューが Django の messages に入れていますが、画面に出す場所がありません。 base.html の MAIN 冒頭に表示領域を追加します。

1-2 「AI監視 稼働中」を実際の状態に連動させる 要修正

サイドバー下部の表示は固定文字です。設定画面でAIを停止しても変わらないため、AISettings.enabled を渡して切り替えます。

他のスタッフが停止した場合も反映されるよう、既存のポーリングAPIに1項目足します。

1-3 ログイン後の遷移先を直す 要修正

login.html の next が /dev/var6/ に固定されています。 公開サーバーをそのパス配下で動かすための対応と思われますが、テンプレートに直書きするとローカルで動きません。 テンプレートは標準の {{ next }} に戻し、サブパスは設定で吸収します。

補足 STATIC_URL = "static/" は既に相対指定なので、FORCE_SCRIPT_NAME を設定すれば静的ファイルのURLにも接頭辞が付きます。 また ALLOWED_HOSTS に先頭に空白が入った値が1つあります。そのホスト名では一致しないので、空白を削除してください。

1-4 通知のURL直書きをなくす 要修正

app.js の OS通知が /static/img/thumb_fall.svg と /alerts/ を直書きしています。1-3 でサブパス配信にすると壊れるため、テンプレートから渡します。

同じ理由で、core/ai_simulator.py 内の "/static/img/thumb_fall.svg" も settings.STATIC_URL + "img/thumb_fall.svg" に変えておきます(views.settings の手動検知も同様)。

STEP 8. リアルタイムAI(転倒・状態判定)

カメラ映像から異常を検知し、アラートと録画を作る本体です。処理の流れは次のとおりです。

カメラ映像→MediaPipe Pose
(33点×x,y,z = 99値)→ 直近30フレームを保持→転倒LSTM / 状態LSTM→ 閾値判定→Alert 作成 + 8秒録画

学習材料はリポジトリに入っています。train_data/ の CSV は1行が1フレームで、 99個の数値 + ラベル(fall / normal)+ 人物番号の101列です(ヘッダ行なし)。 train_dataset/ には状態モデル用に加工済みのデータ(301件 × 30フレーム × 99値、8クラス: 立っている/座っている/しゃがんでいる/歩いている/前かがみ/横になっている/立ち上がる/転倒)があります。

8-1 モデルの準備と学習 未実装

(a) 姿勢推定モデルをダウンロード

(b) 学習用の共通処理

(c) 学習コマンド

精度について train_dataset/retrain_state.json には、以前のモデルで「正解率 約97% / 見逃し率 約17%」という記録があります。 見逃しを減らすには転倒側のデータ追加が有効です。また上のサンプルは同じCSVから切り出したデータが学習用と検証用の両方に入るため、 検証精度は実力より高めに出ます。厳密に測るときはCSVファイル単位で学習用/検証用を分けてください。 STRIDE やモデルの層構成は元の実装と同じとは限りません(元コードがリポジトリに無いため)。

8-2 解析エンジン 未実装

カメラ1台につき1スレッドで解析します。画面のAIカードに出す値(状態/判定/危険度/足の位置/無動作/解析フレーム/fps/自動録画)は、 すべてこのエンジンの status が元になります。

画面項目の定義について 「足の位置」は元の実装の定義がリポジトリから読み取れないため、サンプルでは 「足首が画面下端からどの高さにあるか」としています。元の意味が分かる場合は foot の計算を差し替えてください。 「自動再学習 最終: …」の表示も、元の実装(起動時に学習データの変更を検知して再学習)が無いため retrain=None(非表示)にしています。

8-3 起動制御(シミュレーターと常時稼働) 要修正

現在の apps.py は migrate や seed_demo の実行時にもシミュレーターを起動します。 「Webサーバーとして動いている時だけ」「設定で有効な時だけ」に絞ります。

実AIに切り替える時の設定 AI_REALTIME_ENABLED = True にしたら、AI_SIMULATOR_ENABLED = False にしてください。 両方 True だと、乱数の異常と本物の異常が混ざります。
未使用の core/ai_monitor.py は旧版のシミュレーターで、どこからも呼ばれていません (PersonState の import 漏れもあり、呼ぶと動きません)。削除して構いません。

8-4 映像配信をエンジン経由に切り替える 未実装

AIが読んでいるカメラを配信側も直接読むと、1枚のフレームを取り合ってどちらかが欠けます。 AI有効時はエンジンが描画済みの最新画像を配る形にします。

最後に、AIカードを1秒ごとに更新するJSを追加します。

8-5 立ち入り禁止ゾーンの検知 未実装

異常の種類に「立ち入り禁止ゾーン」がありますが、実検知の仕組みがありません。 カメラごとに禁止エリア(多角形)を登録し、足の位置がその中に入ったら異常にします。

解析ループの「異常の判定」に、次の分岐を足します。足の位置は両足首の中点を使います。 禁止エリアの値は毎フレームDBを読まないよう、AI設定と同じタイミング(1秒ごと)で読み直してください。

Recording.Kind には zone が無いため、_write_recording では既存のシミュレーターと同じく 「あやしい場面」として保存されます(サンプルはその動作になっています)。 禁止エリアは管理画面(/admin/)のカメラ編集でJSONとして入力できます。

11(STEP 8 後)安全な場所で転倒動作をする異常が1件作られ、約8秒後に録画一覧へ実映像が出る。一覧のサムネイルが実画像になる
12(STEP 8 後)無動作検知の秒数ぶん静止する「あやしい動き」の異常が作られる

C. 本番公開の前に必要な設定

  • SECRET_KEY がソースに直書きされています。環境変数から読む形に変え、値を作り直してください。
  • DEBUG = False にする。その場合 static/ と media/ は Nginx などから配信します(動画の途中再生に必要な範囲指定リクエストにも対応できます)。
  • 解析エンジンはWebサーバーと同じプロセス内で動きます。gunicorn を使う場合はワーカー1・スレッド複数(例: --workers 1 --threads 8)にしてください。ワーカーを増やすとカメラを取り合います。
  • 8-3 の起動判定は runserver を前提にしています。gunicorn で動かす場合は、環境変数(例: CARESEC_BACKGROUND=1)でも起動できるよう条件を足してください。
  • encrypt_db.py は検証用の簡易的な方式です。AWS構成図.md の方針どおり、本番はディスクの暗号化を使ってください。
